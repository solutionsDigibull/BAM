# SBAM Architecture Overview (developer edition)

This is the short version. The full detail is in the [design pages](design/README.md) (TD), the [phase pages](phases/README.md) and the [plan pages](plan/README.md) (PLAN).

---

## 1. Where SBAM sits in BuLLM

```text
SBAM (build-time: build, validate, certify)  ──frozen certified manifest──►  SRIM (runtime: execute)
                                                                              BuLLML (intelligence)
                                                                              BuLLMind (reporting)
```

SBAM ends when a Workflow is **certified, frozen and exported**. Deployment, hot-reload and execution belong to SRIM and are **out of scope**. The automated SRIM handover API is future scope; in the MVP the handover is a downloadable, checksummed export package.

## 2. Users

| Role | Portal | Does |
|---|---|---|
| **Admin** | Admin portal | Creates **projects**, maintains the **five masters** (Organization, Rules, Agents, Skills, Filetype + README) and users/RBAC |
| **FDE** (Forward Deployed Engineer) | FDE portal | **Drives the pipeline** in an assigned project: upload → review/approve SOW → review ISATVON → Generate → retry → export |
| **Super-admin** | Admin portal | Creates tenants; only role that may change the frozen Filetype table |

Multi-tenant: client organisations are fully isolated (Keycloak organizations + `tenant_id` on every row).

## 3. Hierarchy (memorise this)

```text
Tenant
 └── Project                     created by the Admin; holds masters context; FDEs assigned
      ├── Documents              uploaded by the FDE (≤20 files, ≤15 MB each)
      ├── Knowledge version      Cognee graph + OKF bundle
      ├── SOW                    generated in one shot; FDE edits + approves
      └── Workflow               ★ GENERATED BY SBAM from the approved SOW (never created by the FDE)
           └── Macro Skill       "agent", id MSnn  (e.g. MS01_Investor_Registration_Access)
                └── Sub-Skill    "skill", id MSnn.m (e.g. MS01.1_Investor_Auth_Manager)
                     ├── ISATVON 1.4 definition (I, S, A, T, V with 5 loop bounds, O with state handoff, N)
                     ├── Skill Manifest (exact ISATVON 1.4 manifest format + sbam_build_record)
                     ├── Code: Action tool + independent Fixed Check tool + state-handoff writer (FastMCP)
                     ├── Gates: AST, Ruff, Black, MyPy strict, Bandit, ClamAV, imports, schema.sql
                     ├── ≥3 loop scenarios run by the loop harness in CubeSandbox (Promptfoo assertions)
                     └── Certification (automatic)
```

## 4. End-to-end flow

```text
[Admin] Project + masters ─────────────────────────────────┐ context
[FDE] Upload (Uppy) → ClamAV → parse/OCR → Cognee → OKF bundle → LLM → SOW v1
      → FDE edits (TipTap) → FDE approves  ──► SBAM creates the Workflow
      → ISATVON 1.4 breakdown (Macro → Sub-Skills) → FDE reviews in AG Grid → Generate
      → per Sub-Skill (parallel): Skill Manifest → Jinja2 skeleton + LLM bodies → AST + static gates
        → LLM test data → loop harness in CubeSandbox + Promptfoo → auto-certify
        (failure → up to 2 LLM corrections → back to FDE)
      → Macro certified → Workflow validated + certified → versioned (MAJOR.0.PATCH) → frozen → export
```

Orchestration: one `ProjectPipeline` Temporal workflow per project, plus one `SubSkillBuild` child per Sub-Skill (TD §13).

## 7. Golden rules (non-negotiable)

1. **The FDE never creates a Workflow.** SBAM generates it when the SOW is approved. No API or UI path lets an FDE create one.
2. **Contracts are the single source of truth.** ISATVON 1.4, Skill Manifest, masters and SOW models live in `server/contracts`. TS types are generated and never hand-edited.
3. **Tenant isolation everywhere.** Every row has `tenant_id`/`project_id`; cross-tenant access returns 404; Cognee dataset, storage path, prompts and sandbox runs are per project.
4. **LLM output is untrusted.** Always schema-validate it. It never triggers state changes on its own. All calls go through Bifrost aliases.
5. **Masters structure is frozen (BAM 0.2).** Never add, rename or reorder workbook columns. Stable IDs and status are read from inside rows. The 43 filetypes are a private read-only table.
6. **ISATVON 1.4 loop semantics.** Iteration is declarative (5 bounds in V). Generated code has **no manual retry loops**. The check tool never imports or calls the action tool. The state handoff is **append-only**.
7. **Certification is automatic and all-or-nothing.** A Sub-Skill certifies only when every gate passes on one code hash, including ≥3 loop scenarios in **certifying CubeSandbox**. Local-docker sandbox runs never certify.
8. **Certified means frozen.** No edit, update or delete on frozen records or files. Any change creates a new version: MAJOR for a new approved SOW, PATCH for a rebuild under the same SOW. Unchanged parts reuse their certification.
9. **Long work runs in Temporal.** API handlers stay fast; activities are idempotent; workflow code is deterministic.
10. **Everything runs in Docker,** and the skill-runtime image digest is recorded in every manifest.

## 8. Glossary

| Term | Meaning |
|---|---|
| **ISATVON** | Instructions, Source, Automation, Tech stack, Variables, Outcome, Notification: the skill contract (v1.4) |
| **Loop bounds** | `max_iterations`, `success_gate`, `no_op_condition`, `escalation_condition`, `budget_limit` |
| **Action tool / Fixed Check tool** | The FastMCP tool that does the work, and the independent tool that verifies it |
| **State handoff** | Append-only audit record written by every run (ISATVON O) |
| **OKF bundle** | Open Knowledge Format package of the project's knowledge (full text + entities + relations + provenance) |
| **Masters** | Admin context: Organization, Rules, Agents, Skills, Filetype (+ README), BAM 0.2 structure |
| **Skill Manifest** | Per-Sub-Skill JSON in the ISATVON 1.4 manifest format (`skill_metadata`, `isatvon_definition`, `srim_runtime_definition`, `contracts`, `governance`) + `sbam_build_record` |
| **Workflow manifest** | The final SBAM output that references all certified skills |
| **Loop harness** | SBAM's test-only emulation of the declarative loop (no-op → action → check → gates per pass) |
| **ProjectPipeline / SubSkillBuild** | The two Temporal workflow types |
| **P / W paths** | API prefixes: project-level `/projects/{id}` vs Workflow-level `/projects/{id}/workflows/{wid}` |
