# TD §12. Code generation (hybrid Jinja2 + LLM)


## 12.1 What is generated per Sub-Skill

| Artifact                                                                                                                                                                      | From     | Generated by                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------ |
| `action_tool.py` — FastMCP tool named after `t_tech_stack.action_tool` implementing `a_automation.action_step`                                                         | Manifest | Jinja2 skeleton + LLM body           |
| `check_tool.py` — independent FastMCP tool named after `fixed_check_tool` implementing `a_automation.acceptance_check` and returning the values `success_gate` needs | Manifest | Jinja2 skeleton + LLM body           |
| `models.py` — Pydantic input/output models from `contracts`                                                                                                              | Manifest | Jinja2 only                          |
| `state_handoff.py` — append-only writer for `o_outcome.state_handoff_file` (insert only, never update/delete)                                                            | Manifest | Jinja2 only                          |
| `state.py` — reader for `fresh_state_parameters` (re-read every iteration)                                                                                               | Manifest | Jinja2 skeleton + LLM body (queries) |
| `server.py` — FastMCP server registering both tools                                                                                                                        | Manifest | Jinja2 only                          |
| `loop_spec.json` — the 5 bounds compiled into an evaluable form (for the SRIM runtime and the SBAM sandbox harness)                                                        | V        | Platform                             |
| Sub-Skill DDL fragment (`schema.sql`) for tables in `v_variables.tables`                                                                                                  | V, O     | LLM-proposed + validated ([§12.6](12-code-generation.md))    |

**There are no hand-written retry loops.** Iteration is declarative (V bounds) and executed by the runtime. In SBAM it is emulated by the sandbox loop harness ([§15.2](15-test-data-promptfoo-and-sandbox-design.md)).

## 12.2 Pipeline

```text
Skill Manifest
 → Jinja2 skeleton render (deterministic): server, models, state reader stub, handoff writer,
   action/check tool signatures + docstrings, protected LLM slots
 → LLM bodies (sbam-codegen → CodeBodies {action_body, check_body, state_queries, helpers})
 → Assembly → Black → bundle + per-file hashes
 → AST gate (§12.5) → Static/security gate (§12.6)
 → Tests in CubeSandbox with the loop harness + Promptfoo (§15)
 → fail → Correction (≤2) → re-run;   pass → certify
```

## 12.3 Skeleton template layout

```text
templates/fastmcp-loopy/1.0.0/
  template.yaml            name, version, supports_isatvon ["1.4"], params_schema, base_imports
  server.py.j2             FastMCP app; registers action + check tools
  models.py.j2             Pydantic models from contracts.input_schema / output_schema
  action_tool.py.j2        @tool action: signature, docstring (action_step) + LLM_BODY:action slot
  check_tool.py.j2         @tool check: signature, docstring (acceptance_check) + LLM_BODY:check slot
  state.py.j2              fresh-state reader: LLM_BODY:state_queries slot (parameterised SQL only)
  state_handoff.py.j2      append-only INSERT into the handoff table (no slot)
  tests/golden/            manifest fixtures → expected skeleton output
```

Rules: templates are owned by the platform team in Git (O-06), semver + hash. Jinja2 `SandboxedEnvironment` + `StrictUndefined`. Manifest text is inserted only as escaped literals/docstrings. The LLM returns only slot bodies and helpers.

## 12.4 Correction (C-24)

| Attempt | Input to`sbam-corrector`                                                          | Allowed changes                                                             | Then                                                                                           |
| ------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1       | Failing findings (gate, message, location, harness trace), manifest, current bodies | Patch`isatvon_definition` (e.g., bounds, gates, schema) and/or new bodies | Re-manifest if ISATVON changed → re-render → all gates and tests again                       |
| 2       | Same + attempt-1 diff and results                                                   | Same                                                                        | All gates and tests again                                                                      |
| after 2 | —                                                                                  | —                                                                          | `NEEDS_FDE_REVIEW` + notification; the FDE edits and clicks **Retry** (counter resets) |

Correction patches to ISATVON are recorded as edits by `sbam-corrector` and shown to the FDE.

## 12.5 AST gate (validation against the manifest)

| Check              | Rule                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AST_SYNTAX         | `ast.parse()` succeeds for every file                                                                                                                                                                                                                                                                                  |
| AST_SKELETON       | Non-slot regions are AST-identical to the freshly rendered skeleton                                                                                                                                                                                                                                                      |
| AST_CONFORMANCE    | Tools named as`action_tool` and `fixed_check_tool` exist and are registered; parameters match `contracts.input_schema` (names, annotations); outputs match `contracts.output_schema`; the check tool returns every identifier used by `success_gate`/`escalation_condition` that is not an input/state/bound |
| AST_DECOUPLING     | `check_tool.py` does not import `action_tool.py` (or vice versa) and does not call the action; shared code only via `models.py`/`state.py`                                                                                                                                                                       |
| AST_NO_MANUAL_LOOP | No`while` loops and no retry decorators/loops in tool bodies (iteration is declarative) *(bounded `for` over data collections allowed)*                                                                                                                                                                            |
| AST_HANDOFF        | The action path calls`state_handoff.append(...)` with every `required_fields` key; no UPDATE/DELETE against the handoff table (SQL string scan)                                                                                                                                                                      |
| AST_IMPORTS        | Imports ⊆ template base imports ∪ registry-resolved`libraries`. Forbidden: `eval`, `exec`, `compile`, `__import__`, `os.system`, `subprocess` (unless declared), `pickle`, `marshal`, `ctypes`                                                                                                     |
| AST_SQL_SAFETY     | SQL is parameterised only (no f-string/concatenated SQL)                                                                                                                                                                                                                                                                 |

The gate re-reads the stored bundle and checks it against the hashes `assemble` recorded before it
looks at any code, and never imports or runs it. Its verdicts are `gate_results` rows, one per gate
and build stage key, each carrying the `code_attempt_id` and the `bundle_sha256` it judged; a row
about another attempt or another bundle is refused, never reused, and a retry reads the rows it
already wrote. A failed check raises `GateFailed` (the correction loop, §12.4). A bundle that no
longer matches its recorded hashes (`BUNDLE_TAMPERED`), or a gate handed inputs that are not the
attempt's (`AST_GATE_INPUT_MISMATCH`), is a platform defect: the Sub-Skill goes to `BUILD_ERROR` and
a notification names the cause (E31, E32).

## 12.6 Static and security gate, and schema SQL

| Gate              | Tool                                                                                          | Blocking rule                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| RUFF              | Ruff (pinned config)                                                                          | Any error                                                                                                                                |
| BLACK             | `black --check`                                                                             | Any diff                                                                                                                                 |
| MYPY              | `mypy --strict`                                                                             | Any error                                                                                                                                |
| CLAMAV            | clamd scan of bundle                                                                          | Any detection                                                                                                                            |
| BANDIT*(O-03)*  | Bandit                                                                                        | HIGH blocks; MEDIUM reported                                                                                                             |
| IMPORT_RESOLUTION | Import all modules in`skill-runtime`                                                        | Any ImportError                                                                                                                          |
| SCHEMA_SQL        | Parse DDL (`sqlglot`, postgres dialect) against a DDL allowlist and apply it to a throwaway database on the isolated `schema-check` PostgreSQL (E9.4) | Parse/apply error; forbidden statement; declared table missing; two Sub-Skills defining one table differently; handoff table without the insert-only guard (a trigger rejecting UPDATE/DELETE and one rejecting TRUNCATE) |

How E12.4 runs the first five gates (`static_gate`, `sbam_workers/build/gates/static_gate.py`):

- **Input.** The stored bundle of the code attempt, re-read and checked against the hashes `assemble` recorded (a mismatch is `BUNDLE_TAMPERED`, E31). Each verdict is a `gate_results` row on that `bundle_sha256`.
- **Tools.** Nothing executes generated code. Black runs in process; Ruff, MyPy (`--strict`, `--no-site-packages`) and Bandit run as separate Python processes on a scratch copy, with an empty environment and a timeout. Their versions are pinned in the worker's lockfile and the configs (`ruff.toml`, `mypy.ini`, the Black mode) are stored by sha256 as `config_sha256`, so a run can be reproduced. Findings are normalised to `{gate, code, file, line, severity, message}` and sorted. Ruff, Black and MyPy findings are HIGH; Bandit keeps its own severity.
- **Blocking.** Any Ruff, Black or MyPy finding, a Bandit HIGH, any ClamAV detection. A Bandit MEDIUM or LOW is reported on a passing verdict. A blocking failure raises `GateFailed` with the attempt id and the build corrects it from the stored findings.
- **ClamAV.** Every file of the bundle goes to clamd (INSTREAM) after a VERSION check; signatures older than 24 hours are an infrastructure error. A detection also copies the bundle to quarantine storage, writes a `BUNDLE_QUARANTINED` audit row and logs an operator alert.
- **No verdict.** A tool timeout or crash, clamd unreachable or stale signatures raise a retryable `STATIC_GATE_INFRA` (2 attempts). It never reaches the correction loop; after the retries the build stops as `BUILD_ERROR` with a notification (E33). Nothing is recorded for a gate that gave no verdict.
- **Not here.** `IMPORT_RESOLUTION` needs the `skill-runtime` image and is its own stage. The network-less, read-only, non-root toolchain container of the issue text is a deployment hardening of the worker, tracked separately; the tools here already need no network and run in a scratch directory with an empty environment.

**Foundational schema (ISA14 "Contract-Driven Development"):** ISA14 states that ISATVON is fed to coding agents "alongside a foundational PostgreSQL .sql schema file". SBAM handles this as follows (O-16, built in E9.4):

1. If the FDE uploaded a `.sql` file (Filetype master supports `.sql`), it becomes the base schema.
2. Otherwise SBAM generates DDL for every table in `v_variables.tables` (LLM-proposed, validated by the SCHEMA_SQL gate).
3. The Workflow-level `schema.sql` merges all fragments, is validated once, is used by every sandbox run and is shipped in the export package.

How E9.4 builds it (`build_schema_sql`, `sbam_workers/build/schema_sql/`, once per build before the Sub-Skill builds):

- **Allowlist.** Uploaded and generated SQL is data: it is split with the PostgreSQL tokenizer and each statement must be `CREATE TABLE` (with a column list), `CREATE INDEX`, `CREATE TRIGGER`, a `plpgsql`/`sql` `CREATE FUNCTION` without dynamic SQL or server file/program access, or `CREATE EXTENSION` of `pgcrypto`, `uuid-ossp`, `citext`. Anything else is `FORBIDDEN_STATEMENT`. Generated fragments may only hold `CREATE TABLE` / `CREATE INDEX`.
- **Generation.** One `sbam-codegen` call (prompt `schema-ddl`) per Sub-Skill, in `skill_id` order, for the tables it declares that neither the base nor an earlier Sub-Skill defines; failures are re-asked (at most 3), then become findings.
- **Merge** (deterministic): the base verbatim, then generated tables (referenced tables first, else by name), functions, indexes and triggers, then the guards. One table defined twice the same way is kept once; defined differently it is `CONFLICT`. Table names must be lower-case unquoted identifiers and not PostgreSQL reserved words (`INVALID_TABLE_NAME`).
- **Guard.** A platform template, never model output: `sbam_handoff_insert_only()` with a row trigger `BEFORE UPDATE OR DELETE` and a statement trigger `BEFORE TRUNCATE` on every handoff table, appended even when the base defines the table.
- **Apply.** The `schema-check` PostgreSQL 16 (Compose; tmpfs, trust auth, no published port, on its own internal network with `worker-build` only, never SBAM's database): a throwaway database per check, the script in one transaction, then every declared table must exist and every handoff table must refuse TRUNCATE (and UPDATE/DELETE on a probe row when one can be inserted). The database is dropped afterwards.
- **Records.** The script is stored (`artifacts` kind `SCHEMA_SQL`), a `workflow_schemas` version and a Workflow-level `gate_results` row hold the verdict and findings; the Skill Manifest records the latest PASSED `sha256` as `schema_sql_sha256`. FAILED raises the non-retryable `SchemaInvalid` (the pipeline notifies the FDE); `schema-check` unreachable is retried (2 attempts).
