## 2. Terminology and hierarchy

```text
Tenant (client organisation, isolated)
 └── Project            created by Admin (Admin portal); holds masters context; FDEs assigned
      ├── Documents (uploads, ≤20 per project, ≤15 MB each)        ← FDE uploads and drives the pipeline
      ├── Knowledge version (Cognee graph + OKF Bundle)
      ├── SOW (versions; FDE approves one version)
      └── Workflow      generated by SBAM from an approved SOW version (never created by the FDE);
           │            the unit that is finally certified + frozen
           └── Macro Skills  (= agents, id MSnn: major modules of the solution)
                └── Sub-Skills (= skills, id MSnn.m: smallest implementable features)
                     ├── ISATVON 1.4 definition (I, S, A, T, V incl. 5 loop bounds, O incl. state handoff, N)
                     ├── Skill Manifest (ISATVON 1.4 format + sbam_build_record) — contract for code generation
                     ├── Code attempts       (Jinja2 skeleton + LLM bodies → Action tool + Fixed Check tool)
                     ├── Gate results        (AST, Ruff, Black, MyPy, ClamAV, Bandit, imports, schema SQL)
                     ├── Test dataset + ≥3 loop scenarios (Promptfoo) run by the loop harness in CubeSandbox
                     └── Certification       (auto; manifest lifecycle = APPROVED)
           Workflow manifest = all certified Macro Skills + Sub-Skill manifests → certified → frozen → export
```

| Term                        | Meaning                                                                                                              |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Admin**             | Keycloak role`sbam-admin`; uses the Admin portal: projects, masters, RBAC.                                         |
| **FDE** | Keycloak role `sbam-fde`; uses the FDE portal to drive the project pipeline: upload, review/approve SOW, review ISATVON, Generate, retry, export. **Never creates a Workflow.** |
| **Super-admin**       | Platform role that creates tenants (O-11).                                                                           |
| **Workflow** | SBAM business object generated by SBAM from an approved SOW version (never a Temporal workflow; never created by the FDE). |
| **Temporal workflow** | Durable execution in Temporal (`ProjectPipeline`, `SubSkillBuild`, …).                                         |
| **Certified**         | All gates passed (automatic).**Frozen** = certified and immutable.                                             |
| **N field**           | "Next / Notification": an in-app notification, then advance to the next step (C-18).                                 |

### 5.2 Ingestion pipeline (Dev B)

- tusd `pre-create` hook → API checks token, project, file count, size and extension. `post-finish` hook → API registers the version and signals the `DocumentIngestion` Temporal workflow.
- **The Filetype master drives ingestion.** The 43 frozen Filetype entries (format, RAG tier, purpose, RAG ingestion method) each map to a loader. A type is accepted only if SBAM has an `mvp_enabled` loader for it. The flag lives in platform configuration, not in the frozen tab. MVP loaders:

| Filetype master entries                                                                                                 | RAG tier | MVP loader                                                                                                                              | MVP                            |
| ----------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `.md`, `.txt`                                                                                                       | 1        | Cognee TextLoader (headings/structure preserved)                                                                                        | ✔                             |
| `.eml`, `.msg`                                                                                                      | 1        | Email parser: headers, body, attachments as child documents (also scanned)                                                              | ✔                             |
| `.json`, `.xml`, `.yaml`, OpenAPI, Swagger, FastMCP Spec                                                          | 1        | Structural pre-parse → text + key paths, then Cognee                                                                                   | ✔                             |
| `.py`, `.sql`, `.js`, `.go`, `.cpp`                                                                           | 1        | Source as text with symbol extraction (Python`ast`; others plain text in MVP; tree-sitter later)                                      | ✔ (basic)                     |
| `.csv`, `.xlsx`                                                                                                     | 2        | `csv` / `openpyxl` with sheet/cell provenance                                                                                       | ✔                             |
| `.docx`                                                                                                               | 2        | `python-docx` / Cognee UnstructuredLoader                                                                                             | ✔                             |
| `.pdf` (text-based)                                                                                                   | 2        | `pypdf`/`pdfplumber` (text + tables)                                                                                                | ✔                             |
| `.zip`, `.tar.gz`                                                                                                   | 2        | Decompress at the gateway; each member is ingested as its own document (counts toward the 20-file limit; size limit applies to members) | ✔ (P1)                        |
| `.pdf` (scanned), `.png`, `.jpg`, `.jpeg`, `.tiff`                                                            | 3        | Rasterize → LLM vision OCR via Bifrost`sbam-ocr`                                                                                     | ✔ (basic OCR)                 |
| `.parquet`, Google Docs, Google Sheets, Web URL / HTML                                                                | 2/1      | —                                                                                                                                      | Future                         |
| `.dwg`, `.dxf`, `.step`, `.stp`, `.iges`, Gerber RS-274X/X2/X3, ODB++, IPC-2581, `.mp3`, `.wav`, `.mp4` | 3        | —                                                                                                                                      | Future (CAD/PCB/media parsers) |

- Normalized derivative: `doc.md` (Markdown) + `doc.json` (blocks with `page`/`sheet`/`cell`/`line` provenance, tables as arrays).
- OCR: pages without text or image files are rendered to PNG and sent to the `sbam-ocr` vision alias, with an extraction prompt to return Markdown per page.

### 5.3 OKF Bundle (Dev B)

Requirement C-13: the bundle must preserve all ingested information. Structure *(proposed; align with the OKF specification during the Phase 0 spike)*:

```text
okf-bundle/
  bundle.json         id, project_id, workflow_id, knowledge_version, created_at, okf_version,
                      sources[] (document_version_id, sha256, title, type), master_snapshot_ref, sha256 of all parts
  entities.jsonl      id, type, name, attributes, source_refs[] (document_version_id + location)
  relations.jsonl     id, type, from, to, attributes, source_refs[]
  chunks.jsonl        id, document_version_id, location, text (full normalized content, no truncation)
  masters.jsonl       master entries used as context (type, key, version, payload)
  coverage.json       per document: chunks, entities, status
```

- `chunks.jsonl` holds the **full** normalized text of every document, so nothing is lost even if graph extraction misses facts.
- The SOW stage uses `bundle.json` + entities/relations + chunks. If the total exceeds the model context, chunks are ranked per SOW section (graph proximity + embedding similarity) and the selection is recorded in `llm_calls.context_manifest`.

### 5.4 LLM layer (Dev B)

| Alias              | Used for                       | Output type                                       | Notes                  |
| ------------------ | ------------------------------ | ------------------------------------------------- | ---------------------- |
| `sbam-ocr`       | OCR of scanned pages/images    | Markdown per page                                 | Vision-capable model   |
| `sbam-sow`       | One-shot SOW                   | `SowDocument`                                   | Large context model    |
| `sbam-isatvon`   | Macro and Sub-Skill extraction | `list[MacroSkill]`, `list[SubSkill]`          | Strict schema          |
| `sbam-codegen`   | Function bodies                | `CodeBodies`                                    | Code-specialised model |
| `sbam-testgen`   | Test scenarios + data          | `TestSuiteSpec`                                 | —                     |
| `sbam-corrector` | Correction                     | `CorrectionPatch` (ISATVON patch and/or bodies) | Receives findings only |

Model choice per alias is configured in Bifrost (OpenRouter models, "depending on situation", C-41), with a fallback model per alias. Every call writes `llm_calls` and a Langfuse trace (prompt version, model, tokens, latency, cost). Prompts are versioned files in `services/workers/sbam_workers/llm/prompts/`.

## 7. Database design

### 7.1 Conventions

- PostgreSQL 16; schema `sbam`; UUIDv7 keys; `timestamptz` UTC; `created_at/by`, `updated_at`, `row_version` on mutable tables; `deleted_at` for soft delete.
- **Every table has `tenant_id`**, and every project-owned table also has `project_id`. The repository base class always filters by them.
- Status columns are text + `CHECK` constraints generated from the Python enums.
- JSONB for schema-validated documents (ISATVON, manifests, SOW structure) with a `schema_version` column.
- Files never go in the database: only a storage key + SHA-256 + size + content type.
- Frozen rows are protected by `BEFORE UPDATE OR DELETE` triggers (`is_frozen = true` → raise).
- Audit: a normal append-only table (C-42).

## 8. API design

### 8.1 Conventions

- Base `/api/v1`. Admin APIs under `/admin/...` (role `sbam-admin`). FDE APIs under `/projects/{project_id}/workflows/{workflow_id}/...` (role `sbam-fde` + project assignment).
- Auth: `Authorization: Bearer <Keycloak access token>`. Tenant comes from the token claim and must match the resource; a mismatch returns **404**.
- Errors: `application/problem+json` with `type`, `title`, `status`, `detail`, `code`, `errors[]` (`path`, `message`), `correlation_id`.
- Concurrency: `ETag` = `row_version`; writes require `If-Match` (412 if mismatched, 428 if missing).
- Commands that start long work return **202** + a `run` object; clients poll `GET …/runs/{id}` every 3–5 s (SSE optional later).
- Idempotency: `Idempotency-Key` header on Generate/Retry/Export.
- Pagination: `?cursor=&limit=`; filtering `?status=`; sorting `?sort=-created_at`.
- Status codes: 200, 201, 202, 204, 400, 401, 403 (wrong portal/role), 404 (missing or other tenant/project), 409 (state conflict), 412, 413, 415, 422, 423 (locked/frozen), 429, 503.

Paths below are relative to `/api/v1`. **P** = `/projects/{project_id}` (project-level: uploads, documents, knowledge, SOW, pipeline). **W** = `/projects/{project_id}/workflows/{workflow_id}` (the Workflow SBAM generated: Macro/Sub-Skills, builds, manifests, certification, versions). There is no API for an FDE to create a Workflow.

## 10. ISATVON 1.4 contract (Sub-Skill level)

Source: *ISATVON 1.4 for Skill Generation* (version 1.4.0, 29 June 2026), referred to as **ISA14**. Only the contract-relevant content is used here. ISATVON 1.4 is a **Declarative Bounded Iteration** format: each Sub-Skill is "a task with a fixed check". An **Action Step** is followed by an independent **Acceptance Check**, repeated within **5 mandatory loop bounds**. The loop is declarative; it is executed by the runtime (BuLLM DMR in SRIM), not by hand-written Python loops.

### 10.1 Hierarchy and IDs

```text
Approved SOW
 └── Macro Skill (agent)   id: MSnn            macro_category: "MSnn_<Name>"          e.g. MS01_Investor_Registration_Access
      └── Sub-Skill (skill) id: MSnn.m          skill_id:       "MSnn.m_<Name>"        e.g. MS01.1_Investor_Auth_Manager
           └── ISATVON 1.4 definition → Skill Manifest → Action tool + Fixed Check tool → certified
```

- `nn` = two-digit Macro Skill sequence in the Workflow; `m` = Sub-Skill sequence in the Macro; `<Name>` = PascalCase/underscore words. IDs are stable across versions.
- Macro Skills may reference an **Agents master** entry (`AG-*`). Sub-Skills may reference a **Skills master** entry (`SK-*`) and **Rules master** entries (`RULE-*`).

### 10.2 Macro Skill

```text
MacroSkill
├── macro_category: "MSnn_<Name>"        (unique in Workflow)
├── name, description                     (major module / functional area)
├── order: int
├── sow_refs: [section_id]  (min 1)
```

### 10.4 Validation rules (grid revalidation and build stage A)

1. Strict Pydantic validation: every required field is present and non-empty; no type coercion.
2. `skill_id` matches `^MS\d{2}\.\d+_[A-Za-z0-9_]+$`; `macro_category` matches `^MS\d{2}_[A-Za-z0-9_]+$`; the skill_id prefix equals its Macro's `MSnn`.
3. **I/A consistency:** `i_instructions.action` agrees with `a_automation.action_step`; `check` agrees with `acceptance_check`; `bound` mentions the `max_iterations` value. LLM-assisted consistency check plus rule checks.
4. **Decoupling:** `t_tech_stack.action_tool` ≠ `fixed_check_tool`.
5. **Five loop bounds:** all present. `max_iterations` is an integer 1–10 *(upper limit proposed)*. `budget_limit` parses to milliseconds. `success_gate`, `no_op_condition` and `escalation_condition` parse in the SBAM safe expression grammar (comparisons, `AND`/`OR`/`NOT`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `is`, literals). Every identifier they use resolves to an output field, a fresh-state parameter, an input or `max_iterations`.
6. **Contracts:** each `s_source.required_inputs` item becomes a property in `contracts.input_schema` with a type. `o_outcome.json_schema` converts to `contracts.output_schema`, which must also contain `state_handoff_id`.
7. **State handoff:** `o_outcome.state_handoff_file.table` is listed in `v_variables.tables`; `mode` is `append_only`; `required_fields` has at least 1 entry.
8. **Notifications:** `ui_updates` contains at least one iteration-progress message and one escalation/completion message.
9. **Libraries:** every `t_tech_stack.libraries` package exists in the runtime registry (PostgreSQL only; no DuckDB).
10. **Traceability:** `sow_refs` has at least 1 entry. Text fields are length-limited and control characters stripped. Text is data and is never executed as code.

### 10.5 Versioning

The ISATVON framework version (1.4) is recorded in `sbam_build_record.isatvon_framework_version`. The Sub-Skill's own version follows SBAM versioning (C-32, §11.4) and is written to `skill_metadata.version` and `governance.versioning`. A new ISATVON framework version (for example 1.5) is a contract migration with a dedicated ADR.

### 10.6 SOW structure (derived from ISATVON 1.4)

The SOW is generated so it can be broken down mechanically into ISATVON. `SowDocument` sections:

1. **Overview** — client, objective, background, topic, history (→ I.context).
2. **Users and authority** — roles, personas, decision rights (→ I.user_role).
3. **Scope** — in scope / out of scope.
4. **Modules** — one subsection per future Macro Skill (name, purpose, agent role).
5. **Features** — per module, one item per future Sub-Skill. Each item has: trigger; action; check; bound/retry policy; inputs and state to re-read; external data; tools (action vs check); tables used; success criteria; output; audit/handoff record; status messages, DB updates and alerts.
6. **Data and integrations** — sources, APIs, tables.
7. **Rules and constraints** — references to Rules master entries.
8. **Deliverables and acceptance** — outputs and acceptance criteria.
9. **Assumptions and open points.**

Every section and feature item carries `citations[]` (OKF chunk/entity ids → document + location). Feature items have stable ids, which drive Sub-Skill extraction and scope-change impact analysis.

### 11.4 Versioning (C-32)

- Format `MAJOR.0.PATCH`, stored as string in `skill_metadata.version` and as numbers in `governance.versioning` (`minor` is always 0).
- The first freeze is 1.0.0. A new approved SOW version gives MAJOR +1 (2.0.0). A rebuild under the same SOW gives PATCH +1 (1.0.1).
- Unchanged skills (identical `isatvon_definition`, contracts, template version, runtime digest and test suite hash) reuse their certification (`sbam_build_record.certification.reused_from`) and keep their version number.
- There is no revocation. A new version supersedes the old (`governance.lifecycle.state = SUPERSEDED` in SBAM's records; the frozen file itself is never edited).

### 11.5 Hash rule

`governance.deterministic_hash` = `sha256:` + SHA-256 of the RFC 8785 canonical JSON of the manifest, excluding `governance.deterministic_hash`, `sbam_build_record.evidence` and `sbam_build_record.certification`. This matches ISA14's "TO_BE_COMPUTED_ON_SAVE". The Workflow manifest hash includes every skill's `deterministic_hash`, bundle hash and the schema SQL hash. Signing is future scope.

## 12. Code generation (hybrid Jinja2 + LLM)

### 12.1 What is generated per Sub-Skill

| Artifact                                                                                                                                                                      | From     | Generated by                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------ |
| `action_tool.py` — FastMCP tool named after `t_tech_stack.action_tool` implementing `a_automation.action_step`                                                         | Manifest | Jinja2 skeleton + LLM body           |
| `check_tool.py` — independent FastMCP tool named after `fixed_check_tool` implementing `a_automation.acceptance_check` and returning the values `success_gate` needs | Manifest | Jinja2 skeleton + LLM body           |
| `models.py` — Pydantic input/output models from `contracts`                                                                                                              | Manifest | Jinja2 only                          |
| `state_handoff.py` — append-only writer for `o_outcome.state_handoff_file` (insert only, never update/delete)                                                            | Manifest | Jinja2 only                          |
| `state.py` — reader for `fresh_state_parameters` (re-read every iteration)                                                                                               | Manifest | Jinja2 skeleton + LLM body (queries) |
| `server.py` — FastMCP server registering both tools                                                                                                                        | Manifest | Jinja2 only                          |
| `loop_spec.json` — the 5 bounds compiled into an evaluable form (for the SRIM runtime and the SBAM sandbox harness)                                                        | V        | Platform                             |
| Sub-Skill DDL fragment (`schema.sql`) for tables in `v_variables.tables`                                                                                                  | V, O     | LLM-proposed + validated (§12.6)    |

**There are no hand-written retry loops.** Iteration is declarative (V bounds) and executed by the runtime. In SBAM it is emulated by the sandbox loop harness (§15.2).

### 12.2 Pipeline

```text
Skill Manifest
 → Jinja2 skeleton render (deterministic): server, models, state reader stub, handoff writer,
   action/check tool signatures + docstrings, protected LLM slots
 → LLM bodies (sbam-codegen → CodeBodies {action_body, check_body, state_queries, helpers})
 → Assembly → Black → bundle + per-file hashes
 → AST gate (§12.4) → Static/security gate (§12.5)
 → Tests in CubeSandbox with the loop harness + Promptfoo (§15)
 → fail → Correction (≤2) → re-run;   pass → certify
```

### 12.3 Skeleton template layout

```text
templates/fastmcp-loopy/1.0.0/
  template.yaml            name, version, supports_isatvon ["1.4"], params_schema, base_imports
  server.py.j2             FastMCP app; registers action + check tools
  models.py.j2             Pydantic models from contracts.input_schema / output_schema
  action_tool.py.j2        @tool action: signature, docstring (action_step) + LLM_BODY:action slot
  check_tool.py.j2         @tool check: signature, docstring (acceptance_check) + LLM_BODY:check slot
  state.py.j2              fresh-state reader: LLM_BODY:state_queries slot (parameterised SQL only)
  state_handoff.py.j2      append-only INSERT into the handoff table (no slot)
  tests/golden/            manifest fixtures → expected skeleton output
```

Rules: templates are owned by the platform team in Git (O-06), semver + hash. Jinja2 `SandboxedEnvironment` + `StrictUndefined`. Manifest text is inserted only as escaped literals/docstrings. The LLM returns only slot bodies and helpers.

### 12.4 Correction (C-24)

| Attempt | Input to`sbam-corrector`                                                          | Allowed changes                                                             | Then                                                                                           |
| ------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1       | Failing findings (gate, message, location, harness trace), manifest, current bodies | Patch`isatvon_definition` (e.g., bounds, gates, schema) and/or new bodies | Re-manifest if ISATVON changed → re-render → all gates and tests again                       |
| 2       | Same + attempt-1 diff and results                                                   | Same                                                                        | All gates and tests again                                                                      |
| after 2 | —                                                                                  | —                                                                          | `NEEDS_FDE_REVIEW` + notification; the FDE edits and clicks **Retry** (counter resets) |

Correction patches to ISATVON are recorded as edits by `sbam-corrector` and shown to the FDE.

### 12.5 AST gate (validation against the manifest)

| Check              | Rule                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AST_SYNTAX         | `ast.parse()` succeeds for every file                                                                                                                                                                                                                                                                                  |
| AST_SKELETON       | Non-slot regions are AST-identical to the freshly rendered skeleton                                                                                                                                                                                                                                                      |
| AST_CONFORMANCE    | Tools named as`action_tool` and `fixed_check_tool` exist and are registered; parameters match `contracts.input_schema` (names, annotations); outputs match `contracts.output_schema`; the check tool returns every identifier used by `success_gate`/`escalation_condition` that is not an input/state/bound |
| AST_DECOUPLING     | `check_tool.py` does not import `action_tool.py` (or vice versa) and does not call the action; shared code only via `models.py`/`state.py`                                                                                                                                                                       |
| AST_NO_MANUAL_LOOP | No`while` loops and no retry decorators/loops in tool bodies (iteration is declarative) *(bounded `for` over data collections allowed)*                                                                                                                                                                            |
| AST_HANDOFF        | The action path calls`state_handoff.append(...)` with every `required_fields` key; no UPDATE/DELETE against the handoff table (SQL string scan)                                                                                                                                                                      |
| AST_IMPORTS        | Imports ⊆ template base imports ∪ registry-resolved`libraries`. Forbidden: `eval`, `exec`, `compile`, `__import__`, `os.system`, `subprocess` (unless declared), `pickle`, `marshal`, `ctypes`                                                                                                     |
| AST_SQL_SAFETY     | SQL is parameterised only (no f-string/concatenated SQL)                                                                                                                                                                                                                                                                 |

### 12.6 Static and security gate, and schema SQL

| Gate              | Tool                                                                                          | Blocking rule                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| RUFF              | Ruff (pinned config)                                                                          | Any error                                                                                                                                |
| BLACK             | `black --check`                                                                             | Any diff                                                                                                                                 |
| MYPY              | `mypy --strict`                                                                             | Any error                                                                                                                                |
| CLAMAV            | clamd scan of bundle                                                                          | Any detection                                                                                                                            |
| BANDIT*(O-03)*  | Bandit                                                                                        | HIGH blocks; MEDIUM reported                                                                                                             |
| IMPORT_RESOLUTION | Import all modules in`skill-runtime`                                                        | Any ImportError                                                                                                                          |
| SCHEMA_SQL        | Parse DDL (`sqlglot`, postgres dialect *(proposed)*) and apply to an ephemeral PostgreSQL | Parse/apply error; missing handoff table; handoff table without an insert-only guarantee (*proposed*: trigger rejecting UPDATE/DELETE) |

**Foundational schema (ISA14 "Contract-Driven Development"):** ISA14 states that ISATVON is fed to coding agents "alongside a foundational PostgreSQL .sql schema file". SBAM handles this as follows *(proposed, O-16)*:

1. If the FDE uploaded a `.sql` file (Filetype master supports `.sql`), it becomes the base schema.
2. Otherwise SBAM generates DDL for every table in `v_variables.tables` (LLM-proposed, validated by the SCHEMA_SQL gate).
3. The Workflow-level `schema.sql` merges all fragments, is validated once, is used by every sandbox run and is shipped in the export package.

| `SubSkillBuild`                            | `build_manifest` → `check_libraries` → `render_skeleton` → `generate_bodies` → `assemble` → `ast_gate` → `static_gate` → `generate_tests` → `build_promptfoo_suite` → `run_sandbox_tests` (loop harness) → `certify_sub_skill`; on failure `correct` (≤2) then loop; then **wait `retry`**                                                                                                                                 | `retry`, `cancel`                                             |
| `PurgeDeleted` (daily schedule)            | purge documents past`purge_after`                                                                                                                                                                                                                                                                                                                                                                                                                                   | —                                                                |
| `ExportPackage`                            | assemble zip (manifests, code, schema.sql, evidence, checksums)                                                                                                                                                                                                                                                                                                                                                                                                       | —                                                                |

Every stage calls `notify` (N = Next/Notification): an in-app notification plus a state update through the state machine service.

### 13.3 Retries and timeouts

| Activity                                                                              | Retry                                      | Start-to-close          | Non-retryable                   |
| ------------------------------------------------------------------------------------- | ------------------------------------------ | ----------------------- | ------------------------------- |
| `scan_clamav`                                                                       | 5, backoff 5 s×2                          | 2 min                   | `Infected`                    |
| `parse`                                                                             | 3, 10 s×2                                 | 10 min, heartbeat 60 s  | `Unsupported`, `Corrupt`    |
| `ocr_llm`                                                                           | 3                                          | 10 min                  | `Unreadable`                  |
| `build_knowledge` (Cognee)                                                          | 5, 30 s×2                                 | 60 min, heartbeat 2 min | `EmptyCorpus`                 |
| `build_okf_bundle`                                                                  | 3                                          | 15 min                  | `BundleInvalid`               |
| `generate_sow`, `extract_*`, `generate_bodies`, `generate_tests`, `correct` | 3 (transport) + internal schema re-ask ≤3 | 15 min                  | `SchemaInvalidAfterRetries`   |
| `build_schema_sql`                                                                  | 2                                          | 5 min                   | `SchemaInvalid` (→ FDE)      |
| `render_skeleton`, `assemble`                                                     | 2                                          | 2 min                   | `TemplateError`               |
| `ast_gate`, `static_gate`                                                         | 2                                          | 10 min                  | `GateFailed` (→ correction)  |
| `run_sandbox_tests`                                                                 | 3 for infrastructure only                  | 20 min, heartbeat 30 s  | `TestsFailed` (→ correction) |
| `certify_*`, `freeze_and_version`                                                 | 5                                          | 2 min                   | `HashMismatch`                |

Human waits have no timeout; a reminder notification is sent after 3 days *(proposed)*.

### 13.4 Idempotency and recovery

- Activities upsert by natural keys (`sub_skill_id + build_no + attempt + gate`). Storage writes are content-addressed. LLM results are cached by `(temporal_workflow_id, activity_id, attempt)`.
- Freeze is ordered: files → read-only → DB transaction (certification + version + `is_frozen` + lifecycle `APPROVED`) → read-back hash verification. A failure leaves the version not frozen, and a re-run completes it.
- Replay tests of recorded histories run in CI. Workflow-code changes use `workflow.patched`.

## 14. State machines

### 14.1 Project pipeline and Workflow

**(a) Project pipeline** (driven by the FDE, executed by `ProjectPipeline`):

```text
IDLE → INGESTING → KNOWLEDGE_BUILDING → SOW_GENERATING → SOW_REVIEW → SOW_APPROVED → WORKFLOW_CREATED
 failure states: INGESTION_FAILED · KNOWLEDGE_FAILED · SOW_GENERATION_FAILED · CANCELLED
 scope change: new SOW version → SOW_REVIEW → SOW_APPROVED → new Workflow version (next MAJOR)
```

| State | Entered when | Exits via | Actor |
|---|---|---|---|
| IDLE | Project created by Admin | FDE uploads + Start processing → INGESTING | FDE |
| INGESTING | Processing started | all settled → KNOWLEDGE_BUILDING / INGESTION_FAILED | System |
| KNOWLEDGE_BUILDING | Ingestion done | READY → SOW_GENERATING / KNOWLEDGE_FAILED | System |
| SOW_GENERATING | Knowledge ready | SOW v1 → SOW_REVIEW / SOW_GENERATION_FAILED | System |
| SOW_REVIEW | SOW generated or new version | FDE approves → SOW_APPROVED | FDE |
| SOW_APPROVED → WORKFLOW_CREATED | Approval signal | SBAM creates the Workflow for that SOW version | System |

**(b) Workflow** (created by SBAM; never by the FDE):

```text
CREATED → ISATVON_EXTRACTING → ISATVON_REVIEW → BUILDING → CERTIFYING → CERTIFIED → FROZEN
 failure states: EXTRACTION_FAILED · NEEDS_FDE_REVIEW (any Sub-Skill) · WORKFLOW_VALIDATION_FAILED · CANCELLED
 after FROZEN: Sub-Skill patch → BUILDING (next PATCH)   |   new approved SOW version → new Workflow version (next MAJOR)
```

| State | Entered when | Exits via | Actor |
|---|---|---|---|
| CREATED → ISATVON_EXTRACTING | SBAM created the Workflow after SOW approval | Extraction done → ISATVON_REVIEW / EXTRACTION_FAILED | System |
| ISATVON_REVIEW | Breakdown ready | FDE clicks Generate (all valid) → BUILDING | FDE |
| BUILDING | Generate | all Sub-Skills certified → CERTIFYING; any needs review → NEEDS_FDE_REVIEW (others continue) | System |
| CERTIFYING | All Sub-Skills certified | Macros + Workflow certified → CERTIFIED / WORKFLOW_VALIDATION_FAILED | System |
| CERTIFIED → FROZEN | Certified | Freeze + version completed | System |

### 14.2 Document version

`UPLOADED → SCANNING → (REJECTED | PARSING) → (PARSED | PARSE_FAILED)`, plus `DELETED` (soft, restorable for 90 days) → `PURGED`.

### 14.3 SOW version

`GENERATED → IN_REVIEW → APPROVED (locked)`. On scope change, a new version goes `IN_REVIEW` → `APPROVED`, and the previous approved version becomes `SUPERSEDED`. A generation failure ends in `GENERATION_FAILED` → regenerate → `GENERATED`.

### 14.4 Sub-Skill

```text
DRAFT → (VALID | INVALID) ──Generate──► BUILDING
BUILDING: MANIFEST → CODEGEN → AST → STATIC → TESTING (loop harness + Promptfoo in CubeSandbox)
   any gate fails → CORRECTING (attempt 1..2) → back to failing stage
   attempts exhausted → NEEDS_FDE_REVIEW ──FDE fix + Retry──► BUILDING
   sandbox infrastructure down → TESTING_BLOCKED ──auto retry / Retry──► TESTING
TESTING passes → CERTIFIED (manifest governance.lifecycle.state = APPROVED) ──Workflow freeze──► FROZEN
scope change touching this Sub-Skill → INVALIDATED → DRAFT (re-extracted) → …
unchanged on new version → keeps CERTIFIED (reused)
```

Mapping to ISATVON/manifest status values: SBAM `DRAFT`/`VALID`/`INVALID` → `skill_metadata.status = DRAFT`; `BUILDING`/`CORRECTING`/`TESTING` → `VALIDATING`; `CERTIFIED`/`FROZEN` → `APPROVED`; superseded → `SUPERSEDED`.

### 14.5 Macro Skill

`PENDING → BUILDING → CERTIFIED` when every Sub-Skill is CERTIFIED and the intra-macro input/output links resolve. It returns to `BUILDING` if any Sub-Skill is invalidated or patched, and becomes `FROZEN` with the Workflow.

### 14.6 Workflow certification checks

1. Every Macro Skill is CERTIFIED.
2. DAG complete: every required input of every skill is provided by a declared source (S) or an upstream skill output; no cycles.
3. Interface compatibility: upstream `output_schema` fields satisfy downstream `input_schema` types.
4. Workflow `schema.sql` applies cleanly and contains every table in every skill's `v_variables.tables`.
5. Workflow smoke run *(proposed)*: run the skill chain in DAG order through the loop harness on synthetic data.
6. Workflow manifest assembled, hashed and schema-validated.

### 14.7 Transition rules

All transitions go through `sbam.workflows.state_machine` in a DB transaction (row_version check + audit row + notification). Activities call the same service; the UI never sets states directly.

## 15. Test data, Promptfoo and sandbox design

### 15.1 Test generation (C-29, C-30)

| Layer                    | Produced by                                                                           | Content                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deterministic assertions | Platform, from`contracts.output_schema`, `o_outcome.json_schema` and the V bounds | Output schema validity, enum values (e.g.,`auth_status ∈ {…}`), `state_handoff_id` present, handoff row appended with all `required_fields`, iterations ≤ `max_iterations`, cycle time ≤ `budget_limit`, terminal state consistent with `success_gate`/`escalation_condition`                                                                                                      |
| Loop scenarios (≥3)     | `sbam-testgen` LLM from I, S, A, V, O, N                                            | `PASS_FIRST` (success on pass 1), `PASS_AFTER_RETRY` (check fails, then succeeds within bounds), `ESCALATION` (never meets `success_gate` → escalates at `max_iterations`), `NO_OP` (`no_op_condition` true → no action executed), `EDGE` (boundary inputs). **Minimum 3 per Sub-Skill: `PASS_FIRST`, `ESCALATION` and one of `PASS_AFTER_RETRY`/`NO_OP`/`EDGE`.** |
| Test data                | `sbam-testgen` + platform writers                                                   | Inputs per`required_inputs`; initial **fresh-state** rows (seed SQL) per scenario; scripted state changes between iterations for retry scenarios; files (xlsx/csv/json) for `external_data` FILE refs; mock responses for API refs                                                                                                                                                         |
| FDE cases                | FDE in the test panel                                                                 | Optional extra cases; FDE can edit generated cases                                                                                                                                                                                                                                                                                                                                                   |
| N assertions             | Platform                                                                              | Expected`ui_updates` sequence emitted by the harness (e.g., `Looping [Pass 2/3]`, escalation message)                                                                                                                                                                                                                                                                                            |
| Rubric assertions        | Promptfoo`llm-rubric`                                                               | Only for free-text outputs where deterministic checks are impossible                                                                                                                                                                                                                                                                                                                                 |

Rules: at least 3 cases (as above), all must pass, data is always flagged `synthetic`, and the dataset and suite are hashed and stored.

### 15.2 Sandbox execution

```text
SubSkillBuild.run_sandbox_tests
  → adapter.create_vm(template = skill-runtime@digest, cpu, memory, timeout, network policy)
  → upload bundle + loop_spec.json + Workflow schema.sql + dataset (inputs, seed SQL, files, mocks)
  → start ephemeral PostgreSQL inside the VM, apply schema.sql, seed fresh state
  → for each case run the SBAM loop harness (emulates the declarative ISATVON 1.4 loop):
        if no_op_condition(state, inputs): record NO_OP, stop
        for pass in 1..max_iterations:
            re-read fresh_state_parameters
            call action tool (MCP)            ── within budget_limit
            call fixed check tool (MCP)       ── within budget_limit
            emit ui_update "Looping [Pass p/max]"
            if success_gate(outputs, state): record SUCCESS, stop
            if escalation_condition(...):    record ESCALATED, stop
            apply scripted state change (retry scenarios only)
        if no terminal state: record ESCALATED (bound reached)
     capture outputs, harness trace, handoff rows, stdout/stderr, resources
  → collect egress log → destroy VM
  → Promptfoo (sbam-promptfoo container) evaluates outputs + harness trace + handoff rows → results
```

The harness is SBAM's emulation of runtime looping for **testing only**. It does not replace SRIM's BuLLM DMR. Its semantics are documented in `loop_spec.json`, which is part of the manifest package, so SRIM can confirm parity (O-17).

| Concern            | Design                                                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host               | Linux server with KVM running CubeSandbox, reachable only over Netbird from`sbam-worker-test` (C-28, C-47)                                                                                 |
| Template           | Built from`skill-runtime` Docker image; digest pinned in registry and manifest (mechanism confirmed in the Phase 0 spike)                                                                  |
| Network            | Allowed (QA K4) but controlled: default egress only to the`sbam-mock-api` service and hosts in `runtime.network.allowlist`; DNS restricted; all connections logged to `egress_log_key` |
| Mock APIs          | `sbam-mock-api` container serves mocks generated from S.API definitions *(proposed: Prism/WireMock-style)*                                                                               |
| Limits             | Default 60 s per case, 1 vCPU, 1 GB RAM*(proposed)*; per-manifest overrides within policy                                                                                                  |
| Local mode         | `local-docker` adapter (no network except mock API, read-only FS, limits). Results are marked `NON_CERTIFYING` and the certification checklist rejects them.                             |
| Failure categories | IMPORT_ERROR, RUNTIME_ERROR, TIMEOUT, OOM, OUTPUT_SCHEMA_MISMATCH, ASSERTION_FAILED, EGRESS_BLOCKED, INFRA_ERROR                                                                             |

### 20.4 CI/CD (GitHub Actions)

```text
pull_request: lint (ruff, eslint) → types (mypy, tsc) → unit → API → contract drift → Temporal replay
              → hadolint → build images (cache) → Trivy → SBOM → compose smoke (core) → Playwright smoke
main:         same → push images to GHCR (:sha, :main) → deploy dev automatically
release tag:  promote same digests → deploy staging (auto) → E2E suite → manual approval → deploy production
nightly:      rebuild + rescan images; full E2E on staging; frozen-manifest hash verification job
```

Deploy = SSH over Netbird → `docker compose pull` (by digest) → `api-migrate` → `up -d` → health check → automatic rollback to previous digests on failure.

### 20.5 Netbird (C-47)

One Netbird network with groups: `dev-laptops`, `vm-dev`, `vm-staging`, `vm-prod`, `sandbox-host`. Policies: laptops → dev/staging ops ports; workers → sandbox host API; production ops only for the platform group. No database, Temporal or admin UI is exposed publicly.

### 20.6 Backup

Nightly `pg_dump` of all databases + snapshots of the `storage` and `cognee-data` volumes → off-host backup location (S3 later). Retention 30 days *(proposed)*. A monthly restore drill re-verifies all frozen manifest hashes.
